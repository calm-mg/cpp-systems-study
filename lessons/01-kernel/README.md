# 1강: 커널이란 무엇인가

## 이번 강의의 질문

> 우리가 작성한 C++ 프로그램과 컴퓨터 하드웨어 사이에서 커널은 정확히
> 무엇을 하는가?

소켓, 파일 디스크립터, 프로세스를 배우기 전에 이 질문이 먼저 명확해야
한다. 앞으로 등장할 `open()`, `read()`, `socket()`, `send()`는 모두 사용자
프로그램이 커널에 관리 작업을 요청하는 과정이기 때문이다.

## OS와 커널은 같은 말인가

문맥에 따라 OS라는 말을 커널과 거의 같은 뜻으로 쓰기도 하지만 엄밀하게는
범위가 다르다.

```text
운영체제(OS)
├── 커널
├── 시스템 라이브러리
├── 백그라운드 서비스
├── 셸과 기본 명령
└── 사용자 관리 도구
```

**커널(kernel)**은 운영체제의 핵심이며 CPU의 특권 기능을 사용할 수 있는
코드다. 부팅 과정에서 올라온 뒤 시스템의 중심에서 다음 자원을 관리한다.

- CPU 시간과 실행할 스레드
- 프로세스와 프로세스의 상태
- 물리 메모리와 가상 메모리
- 파일과 파일 디스크립터
- 디스크, 키보드, 네트워크 장치 같은 하드웨어
- TCP/IP 상태와 소켓 버퍼
- 사용자와 프로세스의 권한

Linux는 보통 Linux kernel과 그 위의 user space 도구를 합쳐 하나의 Linux
시스템을 구성한다. macOS도 XNU kernel만으로 전체 macOS가 되는 것은 아니다.

## 커널이 필요한 이유

프로그램이 하드웨어와 메모리를 마음대로 조작할 수 있다고 가정해보자.

- 한 프로그램의 버그가 다른 프로그램의 메모리를 덮어쓸 수 있다.
- 여러 프로그램이 동시에 디스크나 네트워크 장치를 제어하려고 충돌한다.
- 악성 프로그램이 다른 사용자의 파일을 바로 읽을 수 있다.
- 어떤 프로그램이 CPU를 영원히 독점할 수 있다.

커널은 자원을 대신 관리하면서 프로그램 사이에 보호 경계를 만든다.

```text
사용자 프로그램 A ─┐
사용자 프로그램 B ─┼─ 요청 ─▶ 커널 ─▶ CPU·메모리·장치
사용자 프로그램 C ─┘
```

프로그램은 커널이 정한 인터페이스를 통해서만 보호된 자원을 요청한다. 이
제어된 진입점이 **시스템 호출(system call)**이다.

## 사용자 모드와 커널 모드

사용자 모드와 커널 모드는 단순히 코드가 저장된 위치를 뜻하지 않는다. CPU가
현재 코드에 허용하는 **권한 수준**을 뜻한다.

### 사용자 모드

일반 C++ 프로그램은 사용자 모드에서 실행된다.

- 자신의 가상 주소 공간만 접근할 수 있다.
- 장치를 직접 제어할 수 없다.
- 페이지 테이블이나 인터럽트 설정을 마음대로 변경할 수 없다.
- 잘못된 메모리에 접근하면 커널이 프로세스에 오류를 전달한다.

### 커널 모드

커널 코드는 높은 권한으로 실행된다.

- 하드웨어와 물리 메모리를 관리할 수 있다.
- 프로세스의 주소 공간과 권한을 검사할 수 있다.
- 장치 드라이버와 네트워크 스택을 실행할 수 있다.
- 문제가 생기면 특정 프로세스가 아니라 시스템 전체에 영향을 줄 수 있다.

이 구분은 CPU와 메모리 관리 장치가 강제한다. 단순한 C++ 접근 제한자나
프로그래밍 관례가 아니다.

## 시스템 호출의 흐름

C++ 프로그램이 파일이나 소켓처럼 커널이 보호하는 자원에 실제 작업을
요청한다고 생각해보자. 커널 진입이 필요한 경우 개념적으로 다음 순서가
일어난다.

```text
1. 사용자 모드에서 C++ 코드 실행
2. 시스템 라이브러리의 POSIX 인터페이스 호출
3. CPU의 특별한 진입 명령으로 커널에 제어 전달
4. 커널이 요청 번호와 인수를 확인
5. 커널이 보호된 자원에 요청된 작업을 수행
6. 결과를 준비하고 사용자 모드로 복귀
7. C++ 코드가 반환값을 사용
```

하지만 **POSIX 함수 호출과 실제 시스템 호출은 항상 1:1 대응하지 않는다.**
시스템 라이브러리가 값을 cache하거나 user space의 공유 정보를 읽을 수 있고,
운영체제가 더 빠른 경로를 제공할 수도 있다. `getpid()`와 `sysconf()`를 호출할
때마다 반드시 CPU가 커널 모드로 진입한다고 단정하면 안 된다.

이번 실험이 보여주는 것은 process ID와 page size가 커널이 관리하는 시스템
상태이고, 프로그램이 POSIX 인터페이스를 통해 그 상태를 얻는다는 사실이다.
특정 호출에서 실제 kernel entry가 일어났는지는 별도의 시스템 호출 tracing으로
관찰해야 한다. 우리가 공통 코드에서 의존하는 것은 내부 시스템 호출 번호가
아니라 POSIX 인터페이스의 동작 계약이다.

### 함수 호출과 시스템 호출

일반 함수 호출은 같은 권한 수준과 주소 공간 안에서 다른 코드로 이동한다.
시스템 호출은 커널의 검증된 진입점을 통과하며 CPU 권한 수준이 바뀐다. 그래서
시스템 호출에는 검증과 경계 통과 비용이 있다.

시스템 호출이 발생했다고 반드시 다른 프로세스로 교체되는 것은 아니다.
사용자 모드에서 커널 모드로 갔다가 같은 스레드로 돌아올 수도 있다. 이것은
**mode switch**이며, 실행 중인 스레드 자체가 바뀌는 **context switch**와
구분해야 한다.

## 커널이 프로세스에 대해 기억하는 것

실행 중인 프로세스는 단순히 기계어 코드 한 덩어리가 아니다. 커널은 각
프로세스에 대해 다음과 같은 상태를 관리한다.

- process ID와 parent process ID
- 실행 중, 대기 중 같은 scheduling 상태
- 가상 주소 공간과 memory mapping
- 열린 파일 디스크립터
- 사용자 및 그룹 권한
- signal 상태
- 소켓과 IPC 자원

이번 실험은 이 중 process ID, parent process ID, memory page size처럼 커널이
관리하는 상태를 POSIX 인터페이스로 읽는다. 각 함수가 호출될 때 실제 kernel
entry가 발생하는지는 OS와 시스템 라이브러리 구현에 따라 달라질 수 있다.

## C++ 실험 읽기

핵심 인터페이스는 다음과 같다.

```cpp
struct ProcessInfo {
  std::int64_t process_id;
  std::int64_t parent_process_id;
  std::int64_t page_size;
};

ProcessInfo read_process_info();
```

구현에서는 세 가지 POSIX 함수를 사용한다.

```cpp
::getpid();
::getppid();
::sysconf(_SC_PAGESIZE);
```

- `getpid()`는 현재 프로세스의 ID를 얻는다.
- `getppid()`는 이 프로세스를 만든 부모 프로세스의 ID를 얻는다.
- `sysconf(_SC_PAGESIZE)`는 이 시스템에서 사용하는 memory page 크기를
  얻는다.

page는 가상 메모리를 관리하는 기본 단위다. page size는 전체 메모리 크기가
아니며, CPU architecture와 OS 환경에 따라 달라질 수 있다.

`sysconf()` 실패를 검사하는 이유도 중요하다. 커널이나 시스템 라이브러리에
요청했다고 항상 성공하는 것은 아니다. 시스템 프로그래밍에서는 반환값과
`errno`를 함께 해석해야 한다.

## 빌드와 실행

저장소 루트에서 실행한다.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
./build/lessons/01-kernel/kernel_boundary
```

출력 형태는 다음과 같다.

```text
User-space C++ requested kernel-managed process information.
process_id=<positive number>
parent_process_id=<zero or positive number>
page_size=<positive number>
```

숫자 자체를 외우지 않는다. 다음 조건을 관찰한다.

- `process_id`는 실행 중인 프로세스를 식별하는 양수다.
- 프로그램을 다시 실행하면 `process_id`가 달라질 수 있다.
- `parent_process_id`는 보통 프로그램을 실행한 shell이나 도구를 가리킨다.
- 같은 장비와 환경에서는 `page_size`가 반복 실행해도 보통 동일하다.
- 서로 다른 architecture나 OS에서는 `page_size`가 다를 수 있다.

`std::cout`도 흥미로운 경계다. 출력 문자열은 먼저 C++ 표준 라이브러리의
user-space buffer에 머물 수 있다. 실제 터미널로 보내야 할 때 라이브러리가
결국 커널의 파일 출력 인터페이스를 사용한다. C++ stream 자체가 커널은
아니다.

## 흔한 오해

### “커널은 CPU다”

아니다. CPU는 하드웨어이고 커널은 CPU의 특권 기능을 이용해 실행되는
소프트웨어다.

### “프로그램이 시스템 호출을 하면 커널 프로세스가 대신 실행된다”

항상 별도의 프로세스가 대신 실행되는 모델은 아니다. 현재 스레드가 커널의
진입점을 통해 커널 코드를 실행한 뒤 사용자 모드로 돌아오는 것으로 이해하는
편이 정확하다.

### “모든 라이브러리 함수가 시스템 호출이다”

아니다. `std::sort()`처럼 user space 안에서 끝나는 함수도 많다. 반대로
`read()`와 `write()` 같은 인터페이스는 보호된 커널 자원을 다루기 위해
시스템 호출 경계를 통과한다.

### “시스템 호출은 context switch다”

반드시 그렇지 않다. 권한 모드 전환과 실행 스레드 교체는 서로 다른 개념이다.
다만 시스템 호출이 I/O를 기다리게 만들면 커널이 다른 스레드를 실행하면서
context switch가 뒤따를 수 있다.

## 직접 확인할 문제

1. 프로그램을 세 번 실행했을 때 어떤 값이 바뀌고 어떤 값이 유지되는가?
2. terminal에서 실행할 때와 IDE에서 실행할 때 parent process ID가 달라질 수
   있는 이유는 무엇인가?
3. user space 프로그램이 다른 프로세스의 메모리를 주소만 안다고 바로 읽을
   수 없는 이유는 무엇인가?
4. 시스템 호출이 일반 함수 호출보다 비싼 이유를 두 가지 설명해보자.
5. `kernel_boundary.cpp`에 잠시 대기하는 코드를 넣고 다른 terminal에서
   `ps`로 해당 PID를 찾으면, 코드의 값과 OS 도구의 값이 일치하는지 확인할
   수 있다.
